Homey-iPad — Signup and Email Verification Implementation
Date: November 4, 2026 (America/Los_Angeles)

IMPLEMENTATION

Signup retains First Name, Last Name, Display Name, Email Address, Password,
and Confirm Password. Shared validation checks trimmed required names, email
format, both password fields and equality. Supabase remains responsible for its
configured password-strength policy. Email is trimmed and lowercased. Duplicate
submissions are blocked; password fields are cleared after the attempt. Passwords
are never persisted by this flow.

Signup supplies first_name, last_name, and display_name as trimmed Auth metadata
and explicitly uses homeyipad://auth/verify-email. The existing database trigger
creates the profile. Signup performs no profile insert/upsert, and a sessionless
Auth response goes directly to Verify Your Email without manufacturing a local
UserProfile. Duplicate-account responses are handled neutrally without exposing
whether an account exists. Transport/rate errors show friendly recovery guidance.

Verify Your Email uses the existing Sky and Sand background/card/buttons, a
verification icon, the requested wording, the pending email, waiting status,
Resend Verification Email and Back to Log In. There is no Continue action.
The centered card is capped at 560 points and scrolls in portrait/landscape.
Semantic fonts support Dynamic Type, readable labels support VoiceOver, and
busy/disabled states protect requests. Visual and accessibility device QA is
still required.

Resend calls SDK 2.53.0 auth.resend(email:type:.signup:emailRedirectTo:) with the
signup redirect. It never calls signup again or uses password recovery. Requests
are serialized and use an absolute 60-second cooldown, including failed requests.
A countdown is derived from the current time, so backgrounding does not freeze
it. Pending context survives termination. A separate latest-email throttle record
survives cancellation/navigation but cannot restore signup or grant authority.
Success and network/rate-limit messages are shown. Supabase may enforce a longer
limit than the local countdown. Every resend rotates the SDK PKCE verifier;
users are told to use the latest email.

HomeyApp routes exact recovery callbacks to the unchanged recovery service and
exact signup callbacks to AuthenticationService. Signup validation requires the
homeyipad scheme, auth host, exact /verify-email path, no credentials/port,
no fragment, and a single bounded alphanumeric/hyphen/underscore code parameter.
Mixed, duplicate or malformed parameters and unrelated routes are rejected.
Error callbacks, expired/consumed links and exchange failures offer resend/login
recovery. Authentication response bodies, tokens, passwords, and callback secrets
are not logged.

The normal Supabase client explicitly uses PKCE with its existing storage identity.
The installed Swift SDK stores its verifier through default Keychain storage, so
it survives termination. exchangeCodeForSession(authCode:) establishes a session;
a subsequent Auth user(jwt:) request confirms identity, emailConfirmedAt,
non-anonymous status and a non-expired session. The authoritative email must
match the normalized pending signup address. Mismatched/exchange-failed sessions
are discarded locally. The isolated password recovery client's storage key and
callback validation are unchanged.

Auth revision checks prevent a stale startup task or profile response from
publishing over a newer callback/account transition. Callback delivery during
another interactive Auth operation or resend is queued; duplicate in-flight and
successful callback delivery does not establish additional authority. SDK Auth
events emitted by explicit operations cannot publish intermediate authentication.
Root-level onOpenURL works with launch, background and foreground URL delivery.
An existing unverified session is rechecked when the scene becomes active.
Sessionless cross-device confirmation still requires authentication.

Pending state stores only email and resend availability. It is presentation context,
never authentication. Verification success, cancellation and account switching
clear pending context. A single latest-email cooldown record contains only email
and a timestamp. No local flag, stored profile or Auth user object grants access.

Password login, session restoration, Auth events, passkey login and device unlock
use email-specific verification. The generic confirmedAt timestamp is no longer
accepted. Profile loading/initialization must finish before .authenticated is
published. A recoverable account-loading screen offers retry or return to Login
when Auth/profile requests fail. Create Home, accept invitation and create
invitation also fetch the authoritative user before invoking existing RPCs.
Device-unlock account binding and the existing protection service are preserved.

Profile initialization fetches the authenticated user's row, verifies its ID,
and fills only missing/blank names from that user's metadata. Updates compare
the previous column value (or null) and are scoped by user ID, preserving concurrent
edits and all other columns. If the trigger row is absent, an authenticated
conflict-ignoring insert repairs it without replacing a concurrent row. One retry
handles transient failures; continued failure blocks Home onboarding and offers
retry. Existing RLS permissions remain required; no anonymous grants, service-role
key, trigger/table changes or backend migrations were introduced.

After verification and profile loading, existing routing loads Homes and pending
invitations: invitation onboarding for eligible invitations, the existing Create/
Join experience for no Homes, and normal selection/dashboard for memberships.
No Home, invitation acceptance, membership or starter meal is created automatically.
The iPhone repository, URL schemes, backend RPCs, App Groups and entitlements
were not modified.

CROSS-DEVICE / MISSING-VERIFIER BEHAVIOR

The email-confirmation endpoint may confirm the email before redirecting to the
app. A code cannot be exchanged on another device without the originating
Keychain verifier. It is also lost after reinstall/Keychain loss or superseded by
a newer resend. This is never bypassed. Open the latest email on the originating
iPad, request another verification email there, or choose Back to Log In and
use email/password after confirmation. Login fetches the authoritative user and
profile. A device with no pending signup context refuses callback exchange and
shows guidance on Login. The verifier is not exported or copied between devices.

Reference: https://supabase.com/docs/guides/auth/sessions/pkce-flow
API signatures and storage behavior were checked against the locally installed
supabase-swift 2.53.0 source rather than newer SDK features.
