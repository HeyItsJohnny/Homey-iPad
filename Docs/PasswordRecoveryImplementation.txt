Homey-iPad native password recovery — implementation report

by both Debug and Release. Neither build registers the iPhone homey scheme.
No entitlements, App Groups, Keychain access groups, associated domains,

- AuthenticationService handles SDK auth events, profile loading, and passkeys.
- SupabaseManager owns the normal household Supabase client.
- Supabase Swift is pinned to 2.53.0. No native URL schemes/handlers existed.

SUPABASE INTEGRATION AND SESSION SECURITY

Recovery uses the same backend and publishable key through an isolated client.
Its Keychain storage namespace is homeyipad.password-recovery. PKCE is explicit;
auto-refresh is disabled for recovery. The SDK persists the verifier in Keychain,
allowing email callbacks after a cold launch. Normal auth cannot overwrite it.

resetPasswordForEmail(email, redirectTo: homeyipad://auth/reset-password) sends
the email. The view validates email format, blocks concurrent requests, applies
a one-minute resend cooldown after success, and gives an account-neutral notice.
Errors are generic; raw Auth errors and callback URLs are never logged here.

Root-level onOpenURL validates the exact scheme, host, and path. Credentialed
URLs, ports, fragments, mixed parameters, duplicate codes, empty codes, and
unrelated URLs cannot establish recovery. Only PKCE callbacks are accepted.
Links issued before this implementation must be replaced with a new request.
The email must be opened on the iPad where the reset was requested.

The installed SDK's exchangeCodeForSession(authCode:) emits signedIn for PKCE,
not passwordRecovery. Explicit recovery state therefore controls presentation.
Only this dedicated client issues recovery challenges; an unrelated normal
sign-in callback cannot use its verifier. There is no cached-session fallback.
Concurrent callback deliveries are ignored while recovery is active. Replays
after dismissal or restart must pass the server's single-use PKCE exchange again.

After exchange, Auth's user(jwt:) verifies the account and checks identity and
session expiration. update(user: UserAttributes(password:)) is reachable only
from validated recovery state, and the account/session is checked again before
updating. Existing household sessions never authorize a recovery update.

The reset view reuses the Sky and Sand background, hero, card, secure fields,
show/hide controls, buttons, and success/error components. It validates nonempty
and matching passwords. Supabase enforces its configured length, character,
strength, and breached-password rules; server policy errors are shown. No
unverified client-side password policy was invented or backend policy changed.
Passwords are held only in transient view state and cleared on success,
cancellation, invalidation, and view disappearance.

Recovery state takes precedence over normal session restoration and auth events.
A different signed-in account stays isolated from the recovery account. Cancel
or failure returns to the preexisting routing, retaining device-lock restrictions.
Success consumes the recovery authority and locally signs out its SDK session.
Back to Login then locally signs out the normal app session and resets existing
account/device state through AuthenticationService. Other devices are not
intentionally signed out. A process exit after exchange requires a new link;
a persisted recovery session never automatically restores password-update UI.
